# F10.0 Public Claim and Privacy Audit

## Purpose and boundary

This document is the source of truth for what eBrain may claim in public README, documentation,
website, package metadata, release notes, and Devpost materials. It is written before public-copy
changes so marketing cannot outrun implementation. It does not make a repository public, push a
branch, deploy a website, rewrite history, inspect private data, or change third-party licensing.

Public copy has three evidence classes:

| Class | Meaning | Copy rule |
| --- | --- | --- |
| Verified | Local implementation plus a focused test or hermetic probe exists | State as present-tense capability with its boundary |
| Configured | The capability exists but requires an optional user-selected dependency or configuration | State the prerequisite and fallback truthfully |
| Planned | No supported end-user path exists yet | Put only in roadmap/future work, never in quickstart or feature lists |

## Public privacy audit

### Findings that block public release

1. The tracked repository contains historical handoffs, sprint/audit artifacts, and agent-control
   files that were written for one operator. Some include personal paths, historical operational
   detail, or identities that do not belong in a public developer-tool repository.
2. The current isolation policy and its tests contain operator-specific client identifiers. The
   implementation is protective locally, but those identifiers are not an acceptable portable OSS
   default or public relationship disclosure.
3. Existing history may contain earlier versions of the same material. Removing files from the
   working tree alone would not create a clean public history.

These findings are intentionally described by category rather than reproducing sensitive contents.
They are release blockers, not permission to weaken isolation or omit security documentation.

### Required remediation before public visibility

1. Replace operator-specific isolation identities with a user-owned local configuration and neutral
   fixtures. Preserve fail-closed behavior, symlink resolution, and clean-install default safety.
2. Define a public-document allowlist and move/rewrite operator runbooks, handoffs, private audit
   transcripts, and personal paths into an untracked/private operational store. Do not merely hide
   them from navigation.
3. Decide with the repository owner whether public release uses a clean new public history/repository or an
   owner-approved history rewrite. This cannot be inferred by the maker and requires explicit
   approval before any destructive or external action.
4. Run a release privacy scanner against the exact candidate tree and the selected history strategy.
   The scanner must report categories and paths to the checker without printing secrets or customer
   content in public artifacts.

## License and dependency audit input

- Root package metadata currently says MIT and must change together with the root license text,
  contributor wording, badges, and release documentation in F10.1.
- The repository includes vendored upstream directories with their own notices/licenses. F10.1 must
  inventory and preserve their upstream terms; it must not imply that root AGPL terms relicense
  independently licensed vendor code.
- The current CI pins the upstream knowledge engine at a specific revision. Public docs must state
  only the verified integration and attribution, not an unsupported warranty about upstream code.

## Documentation contract for F10.2/F10.3

1. All new public files are English, task-oriented, and contain no personal filesystem path,
   credential example, customer/client identity, private SOP body, raw transcript, or token value.
2. README links only to the public allowlist. It presents a scrubbed real terminal/TUI capture and
   a five-minute source-first proof, not a marketing-only landing page.
3. Website pages derive claim text from the same public docs/claim matrix. README and website must
   declare the same supported-agent list, privacy boundary, cost boundary, and planned features.
4. Any code snippet that mutates local state states its confirmation/impact. No public onboarding
   asks users to create/copy OAuth material, tokens, locks, or curl commands by hand.
