# F10.3 Implementation Plan -- Complete Static Documentation Website

## Goal and boundary

Build an isolated `website/` Astro package and expand the public Markdown tree into a complete,
task-oriented documentation experience. It must be useful as the first eBrain screen, not a generic
marketing landing page. It builds locally into static HTML and uses only repository assets. This
phase creates no Vercel project, deployment configuration, preview URL, push, release, or
public-visibility change.

Astro static output needs no Vercel adapter; current official documentation confirms static is the
default and Vercel can build it without additional configuration. That capability is not authority
to deploy. A deploy remains an F11 owner approval action.

## Source-of-truth contract

1. `docs/PUBLIC-DOCUMENTATION.md` and its expanded allowlisted descendants remain the content
   source. Astro's official build-time `glob()` content loader reads only those Markdown paths
   directly from the repository; `website/` contains no copied documentation body.
2. Website route metadata may name a document and assign navigation order, but may not introduce a
   competing product claim. Home-page copy stays bounded by the README and F10.0 matrix.
3. A Markdown-link rewrite maps a source-document link to the corresponding static `/docs/` route.
   Links to root public license/security/contribution/notices go to their source-repository location;
   no link may resolve to a historical handoff, audit, detailed ADR, local path, or token example.
4. Assets are synchronised from committed F10.2 generated SVG source. The website never uses a live
   screenshot, external font, analytics script, provider SDK, or credential.

## Reference study and product distinction

An `agent-browser` audit of Herdr's public home, docs hub, and a guide page established useful
developer-documentation patterns: a clear product/docs boundary, a fast start path, sectioned docs
navigation, an on-page heading index, keyboard-accessible search, previous/next reading flow, and
compact social/source links. eBrain will adopt those interaction patterns only.

It will not copy Herdr text, visual identity, screenshots, comparison claims, plugin claims,
installation commands, agent state model, or documentation source. eBrain remains a dark
terminal-derived control-plane experience with its own accurate feature and privacy boundaries.

## Expanded information architecture

```text
/                               product overview, local proof, and docs entry points
/docs/                          documentation hub: install, launch, memory, and routing paths
/docs/getting-started/*         install, quick start, boot/onboarding, first memory, first workspace
/docs/launch/*                  launch modes, selected workspace, manual sessions, TUI control flow
/docs/memory/*                  layers, context packs, episodes, procedures/skills, workflows
/docs/routing/*                 task signals, profiles/targets, provider boundaries, token telemetry
/docs/architecture/*            daemon/MCP, federation, CKIS relationship, public decisions
/docs/guides/*                  supported agents, privacy, migration, troubleshooting
/docs/reference/*               CLI groups, diagnostics, memory, sessions, routing/cost, TUI, MCP, configuration, JSON contracts
/docs/release/*                 contributor workflow, security/license, readiness, Devpost evidence
```

The documentation hub has four explicit paths rather than asking a user to infer eBrain vocabulary:

1. **Install eBrain:** prerequisites, source install, `ebrain up`, `doctor`, and onboarding.
2. **Launch work:** register/select a workspace, choose manual or guided launch, understand the
   resulting persistent session, and return to it safely.
3. **Build durable memory:** first learning, governed context, episode recall, procedure review, and
   workflow boundaries.
4. **Route and observe work:** task signals, user-controlled profiles/targets, provider boundaries,
   and factual token telemetry.

The landing route provides the wordmark, real sanitised TUI frame, source-first proof, feature
boundaries, and immediate doc navigation. Documentation routes use a persistent desktop sidebar,
an on-this-page index from the source headings, previous/next reading flow, and a mobile navigation
disclosure. A small local search index is generated at build time from the allowlist; it performs no
network request other than fetching its own static JSON and supports keyboard opening/closing.

## Documentation expansion contract

The current concise pages become overview nodes. New pages document every supported user-facing
workflow from the dispatcher and TUI without manufacturing unsupported commands:

| Section | Required pages and scope |
| --- | --- |
| Getting started | Quick start; boot and onboarding; first workspace/session; first durable memory. |
| Launch | Manual launch; guided launch; task signals; workspace selection; session handoff; compact-terminal behavior. |
| Memory | Context packs; episodes; procedures; workflows; bounded retrieval; review and confirmation semantics. |
| Routing | User-owned profiles; targets; provider configuration boundary; token/provider telemetry; cap distinction. |
| Architecture | Loopback daemon; MCP bridge; federation; clean local operation; CKIS relationship; public architecture decisions. |
| Guides | Agent adapters; privacy/source isolation; fixture-only migration scope; daemon troubleshooting; common session failures. |
| Reference | CLI grouped by daily control, memory, workspaces/sessions, routing/cost, workflow/procedure, diagnostics; TUI panels/keys; MCP; configuration; JSON contracts. |
| Release | Contributing, security/license, open-source gates, and evidence/reproducible-demo guidance. |

Every page must define what the command or surface does, what it does not do, prerequisites,
confirmation/side-effect boundary, relevant linked next step, and a factual code example when an
example is safe. Pages may not expose token creation, local credential paths, raw transcript data,
customer identity, personal filesystem data, provider account creation, or a universal model claim.

## Visual and accessibility specification

- No gradients, decorative blobs, stock media, rounded floating-card sections, external web fonts,
  animation, or client-side telemetry.
- Dark terminal-derived palette: near-black canvas, off-white copy, teal focus/links, restrained
  amber and violet only as semantic accents. The existing wordmark and generated terminal frame are
  primary visual assets.
- Desktop (`>= 1180px`): centred `1280px` content frame; `248px` navigation rail, `1px` divider,
  `760px` article measure, and `200px` on-this-page rail; header `64px`; `32px` vertical rhythm.
  The home overview reserves a wide real TUI frame and a compact adjacent start path.
- Medium desktop/tablet (`760px-1179px`): `216px` navigation rail plus flexible article; the
  on-this-page rail becomes an inline content index above the article.
- Tablet (`760px-1079px`): one article column with navigation as a full-width band above content;
  no horizontal overflow.
- Mobile (`<760px`, tested at `393x852`): `20px` side padding, stacked overview, horizontally
  scrollable category navigation, code blocks with deliberate local horizontal scrolling, and a
  full-width TUI frame. Every link has a visible focus ring; the skip link reaches `main`.
- Semantic landmarks: header, labelled primary navigation, main, complementary docs navigation,
  article, footer. Images have useful alt text; heading order begins at one H1; color is not the
  only state indicator; reduced motion needs no special handling because no motion is added.
- Footer social/source icons are accessible icon-only links with visible hover/focus tooltips. They
  point to the eBrain GitHub repository, Eduardo's X profile, and Eduardo's LinkedIn profile. Use
  local Lucide SVG assets for product controls and local static brand assets for GitHub/X, because
  Lucide intentionally does not provide brand icons. LinkedIn uses its compact `in` wordmark with
  an accessible name and tooltip. No social icon comes from a CDN.

## Implementation slices

1. **Content first:** expand the public Markdown source tree and public index, then prove the link
   allowlist, English/public-safety rules, command names, and cross-page next steps before building
   the site.
2. **Static engine:** `website/package.json`, Astro static config, source-rooted content collection,
   navigation metadata, markdown link rewrite, build-time search index, Lucide asset subset sync,
   and source-asset sync script. Prove a static build and route inventory before visual work.
3. **Presentation:** shared layout/header/footer, home route, docs hub, three-rail docs shell,
   content route, search dialog, CSS design tokens, responsive rules, source edit links, social
   icons, and asset references. Keep all public claims bounded by source content.
4. **Contracts and QA:** root-level website/doc contract tests, build-output link/asset/search checks,
   local production preview, agent-browser accessibility and keyboard-search inspection, and
   screenshots at `1440x900` and `393x852`. Fix any overflow, broken route, absent asset,
   inaccessible nav, malformed search result, or claim drift before documentation/commit.

## Verification

- `bun install --cwd website --frozen-lockfile` and `bun run --cwd website build` create only static
  output and do not require an adapter/server runtime.
- Contract tests prove source Markdown, navigation metadata, generated search index, and website
  route inventory are equal; no website source/build output includes forbidden private-path, dotenv,
  token-shaped, or historical navigation patterns; every local rendered link, edit link, asset, and
  search result resolves in `dist/`.
- Inspect built home, docs hub, a detailed guide, and reference page at desktop `1440x900` and mobile
  `393x852` with `agent-browser`: landmarks, source-derived navigation, on-page index, actual SVG,
  icon tooltips, keyboard search, no horizontal page overflow, and no browser console errors.
- Re-run root CLI/TUI suites, docs/asset contract, static checks, diff check, and secret scan.

## Stop conditions

Stop and return to design if Astro cannot render the source allowlist without copying private
material; any required page needs an unverified claim; a link would expose historical content; the
mobile layout cannot remain readable; the build requires an adapter, service, credential, or deploy;
or visual QA needs a live remote environment. Independent review and F10.0 release blockers remain
mandatory after local completion.

## Maker completion record

The maker implementation is complete locally. The isolated Astro package builds 40 static pages
from 38 public documentation routes, including the expanded command reference. It has no deployment
adapter, Vercel configuration, server runtime, analytics, external font, or copied documentation
body. The generated content cache and static output are ignored.

Local verification passed the focused documentation/site contracts, `astro check`, the static build
and output verifier, full CLI/TUI suites, link and private-pattern checks, and desktop/mobile
browser inspection. Mobile visual inspection found and fixed an SVG intrinsic-height regression by
making the terminal proof image preserve its aspect ratio at narrow widths.

This record is not an independent audit or permission to deploy, push, change visibility, or submit
an external form. See [the F10.3 maker report](F10.3-WEBSITE-MAKER-REPORT.md) for the exact
commands, evidence, and required checker focus.
