# Claude Code TUI — behavioral reverse-engineering

Method: this is **behavioral RE only**. No decompilation, no reading of the minified bundle. Everything below comes from Anthropic's public docs at `code.claude.com/docs/en/*` (the vault-side `docs.claude.com/en/docs/claude-code/*` URLs 301-redirect there as of 2026-07) and Anthropic's public CHANGELOG.md (shipped in the npm package, `github.com/anthropics/claude-code`), plus stable, widely-observed usage patterns from having used the product. Every claim below is either a direct citation (URL given) or marked **(observed/inferred)** when it is community/product-usage knowledge not pinned to a specific doc paragraph. Version numbers like `v2.1.xxx` are quoted from the docs verbatim to show how fast this surface moves — treat exact numbers as illustrative, not load-bearing.

## (a) Anatomía de layout

**Two render paths, selected by the `tui` setting** (`"default"` = classic scrolling / `"fullscreen"` = alt-screen). [Fullscreen rendering](https://code.claude.com/docs/en/fullscreen) is described as a "research preview" — draws to the terminal's alternate screen buffer like `vim`/`htop`, renders only visible messages (flat memory in long conversations), and adds mouse support (click-to-position cursor, click-to-expand tool results, click-to-select with auto-copy, `Cmd`/`Ctrl`-click to open links). The **input box stays pinned at the bottom of the screen** in fullscreen mode — "If the input doesn't move while Claude is working, fullscreen rendering is active." Classic mode instead appends to native terminal scrollback (so native `Cmd+F`/tmux copy-mode search still work, at the cost of flicker on fast-streaming output). Default per current docs: `"tui": "fullscreen"`. Source: [fullscreen](https://code.claude.com/docs/en/fullscreen), [terminal-config](https://code.claude.com/docs/en/terminal-config#switch-to-fullscreen-rendering), [settings](https://code.claude.com/docs/en/settings) (`tui` row).

**Input prompt box**: single input area at the bottom with a colored border ("input box border" is a themeable token, see §d). Border color changes by mode: `promptBorder` (default/Manual), `planMode` (plan mode accent), `autoAccept` (accept-edits), `bashBorder` (when a line starts with `!`, entering shell mode). A first-open, second-turn-onward **greyed-out ghost suggestion** appears in the empty input box (seeded from recent git history on first open, then from conversation continuation afterward) — `Tab`/`→` accepts it, typing dismisses it; it is off by default in print/headless mode. Source: [interactive-mode §Prompt suggestions](https://code.claude.com/docs/en/interactive-mode#prompt-suggestions), [terminal-config §Color token reference](https://code.claude.com/docs/en/terminal-config#create-a-custom-theme).

**Status/mode indicator** lives in a status bar above/around the input: Manual mode shows a grey `⏸ manual mode on` badge (as of v2.1.203), `acceptEdits` shows `⏵⏵ accept edits on`, `dontAsk` shows `⏵⏵ don't ask on`. Source: [permission-modes](https://code.claude.com/docs/en/permission-modes).

**Statusline** (bottom, separate from the footer): a fully user-scriptable row — "The status line renders in its own row above the built-in footer badges and does not replace them." It's an arbitrary shell command that receives a JSON blob on stdin (model, cwd, git branch/repo, cost, context-window usage + percentage, rate limits, effort level, vim mode, PR info, worktree info, session id/name) and prints ANSI-colored / OSC-8-hyperlinked text to stdout; can be multi-line; supports a `refreshInterval` for time-based content in addition to event-driven refresh (after each assistant message, `/compact`, permission-mode change, vim-mode toggle, debounced 300ms). `/statusline <description>` auto-generates the script from natural language. Source: [statusline](https://code.claude.com/docs/en/statusline) (extensive — full JSON schema documented).

There is also a distinct **`subagentStatusLine`** setting: a per-row renderer for the "agent panel below the prompt" that shows live subagent/background-task rows (`name · description · token count` by default), driven by the same command-on-stdin pattern but receiving an array of task rows (id, name, type, status, description, model, contextWindowSize, tokenCount…) each refresh tick. Source: [statusline §Subagent status lines](https://code.claude.com/docs/en/statusline#subagent-status-lines).

**Footer**: separate from the statusline row. Shows PR-link badges (clickable, colored by review state: green=approved, yellow=pending, red=changes-requested, gray=draft, refreshes every 60s / after `gh pr`/`git push`), Remote-Control connection pill, and `footerLinksRegexes`-driven clickable badges matching patterns in the transcript (e.g. `PROJ-1234` → issue tracker link) with no custom script needed. System notifications (MCP errors, auto-update, context-low warning) share this row on the right side; verbose mode adds a token counter there too. Source: [interactive-mode §PR review status](https://code.claude.com/docs/en/interactive-mode#pr-review-status), [statusline §Troubleshooting](https://code.claude.com/docs/en/statusline#troubleshooting) (footer notification note), settings.md `footerLinksRegexes` row.

**Spinner + rotating gerund verbs**: this is the famous UX signature and it is **officially documented and user-configurable**, not just folklore — settings.json exposes `spinnerVerbs: {"mode": "append"|"replace", "verbs": [...]}` with the documented example `{"mode": "append", "verbs": ["Pondering", "Crafting"]}`, i.e. Anthropic itself confirms "Pondering" and "Crafting" as built-in defaults. There's a parallel `spinnerTipsEnabled`/`spinnerTipsOverride` mechanism for the contextual *tips* text shown near the spinner (distinct from the verb itself), which can be fully replaced or merged. The wider list of built-in verbs beyond "Pondering"/"Crafting" (community folklore includes words like "Herding", "Percolating", "Puzzling", "Wrangling", "Cogitating", "Ruminating"…) is **(observed/inferred)** — a long-running, widely-discussed Easter egg in the user community, not enumerated in the docs page fetched here. The changelog confirms the spinner has evolved a lot: color warms to amber after ~10s "to signal Claude is still working," turns red when a permission check stalls, and past-tense completion text like `Worked for 5s` is a separate, non-overridable string. Themeable via `claude`/`claudeShimmer` color tokens (the shimmer variant supplies the lighter gradient color for the animation). Source: [settings §Available settings](https://code.claude.com/docs/en/settings) (`spinnerVerbs`, `spinnerTipsEnabled`, `spinnerTipsOverride` rows), CHANGELOG.md lines re: spinner amber/red/shimmer/`spinnerVerbs` (public npm package changelog).

**Tool calls / diffs / todos rendering**: tool calls collapse to a single line by default (MCP calls collapse further, e.g. "Called slack 3 times") and expand with `Ctrl+O` (transcript viewer). File edits render as inline diff blocks with themeable add/remove backgrounds (`diffAdded`, `diffRemoved`, dimmed context variants, word-level highlight tokens `diffAddedWord`/`diffRemovedWord`) — plus a dedicated `/diff` interactive viewer (arrow-key browse across per-turn diffs and files, auto-refreshes on external git state changes). The **task list** ("Claude's to-do checklist") is a separate, toggleable panel (`Ctrl+T`, shows up to 5 items) distinct from the **background-task view** (`/tasks`, running shells/subagents) and from **agent view** (`claude agents`, a full-screen dashboard over *background sessions*, see §e). Source: [interactive-mode §Task list](https://code.claude.com/docs/en/interactive-mode#task-list), [commands](https://code.claude.com/docs/en/commands) (`/diff`, `/tasks` rows), [terminal-config §Color token reference](https://code.claude.com/docs/en/terminal-config#create-a-custom-theme) (diff tokens).

**Header/banner**: no persistent app-title banner inside a normal session (unlike OpenCode's pixel-block wordmark home screen per Eduardo's framing in ADR-003) — the closest analog is the **agent view header**, which shows version, model, working directory, and a session-count summary above the grouped session table. A first-run **welcome screen** exists with promotional banners (capped to one per session as of a recent changelog fix). Source: [agent-view](https://code.claude.com/docs/en/agent-view) screenshot description, CHANGELOG.md ("welcome screen stacking multiple promotional banners" fix).

## (b) Modelo de input

**Modes** (cycled with `Shift+Tab`, current mode shown in the status bar): `default`/"Manual" (reads only) → `acceptEdits` (reads + edits + safe filesystem Bash) → `plan` (research/propose, no edits) → optionally `bypassPermissions` and/or `auto` slot in after `plan` if enabled for the account. A 6th mode, `dontAsk` (only pre-approved tools; for CI), is never in the cycle — set only via `--permission-mode dontAsk`. `auto` mode is the most interesting design point for ebrain: instead of prompting per-action, a **separate classifier model** reviews each action and blocks only things that escalate scope, hit unrecognized infra, or look injection-driven — with documented default block/allow rule categories (destructive git ops, force-push, secret-manager writes, IaC destroy, etc. blocked; local file ops, declared-dependency installs, `.env`→matching-API credential flow allowed). Falls back to per-action prompting after 3 consecutive or 20 total classifier blocks in a session. Source: [permission-modes](https://code.claude.com/docs/en/permission-modes) (very detailed — this is arguably the single most sophisticated piece of the whole product).

**Plan mode** deserves its own callout: `Shift+Tab` or `/plan [description]` enters it; Claude reads/explores but never edits; on completion Claude presents a plan and offers **"Approve and start in auto mode / Approve and accept edits / Approve and review each edit manually / Keep planning with feedback / Refine with Ultraplan (browser-based review)"** — i.e. the plan-approval gate is itself a mode-selection UI, and accepting a plan auto-names the session from its content. `Ctrl+G` opens the pending plan in `$EDITOR` for direct editing before approval. Source: [permission-modes §Analyze before you edit with plan mode](https://code.claude.com/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode).

**`@` file mentions**: `@` triggers file-path autocomplete inline in the prompt. **`!` bash mode**: a line starting with `!` runs the command directly in a real shell (not through Claude), streams output live, adds it to conversation context, and — as of a fairly recent version — Claude auto-responds to the output once it lands (configurable via `respondToBashCommands: false` to restore the old "just add to context" behavior). Supports history-based `Tab` autocomplete and (recent versions) live file-path autocomplete on tokens containing `/`. Exits with `Escape`/`Backspace`/`Ctrl+U` on empty prompt. Pasting text starting with `!` auto-enters shell mode. Source: [interactive-mode §Quick commands](https://code.claude.com/docs/en/interactive-mode#quick-commands), [interactive-mode §Shell mode with ! prefix](https://code.claude.com/docs/en/interactive-mode#shell-mode-with--prefix).

**Keybindings (general controls)** — the full table is large; the load-bearing ones for an ebrain design canon:

| Key | Action |
|---|---|
| `Ctrl+C` | Interrupt running op; empty input → clears; press again → exits |
| `Ctrl+D` | Exit (EOF) |
| `Ctrl+L` | Force full terminal redraw (recover from garbled display) |
| `Ctrl+O` | Toggle transcript viewer (expanded tool calls / MCP calls) |
| `Ctrl+R` | Reverse search over prompt history (100 most recent, scope cycles session→project→all via `Ctrl+S`) |
| `Ctrl+B` | Background the running Bash command/agent (twice inside tmux, due to tmux's own prefix key) |
| `Ctrl+T` | Toggle the to-do task-list panel |
| `Esc` | Interrupt Claude / close a dialog (contextual) |
| `Esc, Esc` | Empty input → open rewind menu; input has text → clear + save to history |
| `Shift+Tab` | Cycle permission modes |
| `Up/Down` or `Ctrl+P`/`Ctrl+N` | Cursor within multi-line input, then command history at buffer edges |

Multiline input has **five** equivalent escapes depending on terminal: `\`+Enter (always works), `Ctrl+J` (always works), `Option+Enter`, native `Shift+Enter` (iTerm2/WezTerm/Ghostty/Kitty/Warp/Apple Terminal/Windows Terminal), or paste-mode. `/terminal-setup` patches VS Code/Cursor/Alacritty/Zed config files to make `Shift+Enter` work there. A full **vim editing mode** exists for the prompt (`/config` → Editor mode → vim), with NORMAL/INSERT/VISUAL modes and a real subset of vim motions/operators/text-objects (block-visual `Ctrl+V` is the one thing not supported). All of this is separately **rebindable** via a `~/.claude/keybindings.json`-style file (vim motions excluded). Source: [interactive-mode](https://code.claude.com/docs/en/interactive-mode) (exhaustive keybinding tables), [terminal-config](https://code.claude.com/docs/en/terminal-config#enter-multiline-prompts).

**Checkpointing / rewind** is the other standout input-adjacent UX: every user prompt is an automatic checkpoint; `Esc,Esc` (or `/rewind`) opens a menu listing every prompt sent this session with options **Restore code and conversation / Restore conversation / Restore code / Summarize from here / Summarize up to here / Never mind**. This decouples "undo" from git entirely (git remains the permanent record; rewind is "local undo" for a session). Source: [checkpointing](https://code.claude.com/docs/en/checkpointing).

**`/btw`** is worth flagging as a distinct interaction pattern: a side-question overlay that sees full conversation context but has **no tool access**, doesn't enter history, and can be invoked mid-turn while Claude is still working on the main task. Framed by the docs as "the inverse of a subagent" (subagent = fresh context + full tools; `/btw` = full context + no tools). This is a genuinely novel small-scoped-question UX pattern. Source: [interactive-mode §Side questions with /btw](https://code.claude.com/docs/en/interactive-mode#side-questions-with-%2Fbtw).

## (c) Slash commands

Two distinct systems that were **explicitly merged**: "Custom commands have been merged into skills. A file at `.claude/commands/deploy.md` and a skill at `.claude/skills/deploy/SKILL.md` both create `/deploy` and work the same way." Source: [skills](https://code.claude.com/docs/en/skills).

**Palette UX**: typing `/` opens a menu of everything invocable — built-in commands, bundled skills, user/project/plugin skills, and MCP-server-exposed prompts (namespaced `/mcp__<server>__<prompt>`). Typing `/` + letters filters live. Not every command is visible to every user (gated by platform/plan). Fullscreen mode adds mouse support to the palette (click a row to accept, hover highlights). Source: [interactive-mode §Commands](https://code.claude.com/docs/en/interactive-mode#commands), [fullscreen §Use the mouse](https://code.claude.com/docs/en/fullscreen#use-the-mouse).

**Custom command authoring**: a directory `<name>/SKILL.md` with YAML frontmatter (`description`, `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`/`disallowed-tools`, `model`, `effort`, `context: fork` + `agent:`, `hooks`, `paths` glob-scoping, `shell`) + markdown body. Three storage tiers: `~/.claude/skills/` (personal, all projects), `.claude/skills/` (project, discovered from cwd up to repo root **and** from nested subdirectories on-demand — monorepo-friendly), plugin `skills/`. Naming collisions resolve enterprise > personal > project, and a name clash across nested dirs produces a directory-qualified command like `/apps/web:deploy`. Arguments substitute via `$ARGUMENTS`, `$ARGUMENTS[N]`/`$N`, or named `$name` (from an `arguments:` frontmatter list); `` !`shell command` `` and fenced ` ```! ` blocks inject **live shell output** into the prompt before Claude ever sees it (pre-processing, not something Claude executes itself) — this is the same "dynamic context injection" idea ebrain's own skill-driven CLI-first design should note. Up to 6 skills can be chained in one message (`/code-review /fix-issue 123`) as of a recent version. Source: [skills](https://code.claude.com/docs/en/skills) — this is the densest single doc page fetched; frontmatter table and command-name-source table are exhaustive.

**Bundled skills vs. true built-ins**: the docs explicitly distinguish "built-in commands whose behavior is coded into the CLI" from "bundled skills," which are "prompt-based: they give Claude detailed instructions and let it orchestrate the work using its tools" (e.g. `/doctor`, `/code-review`, `/batch`, `/debug`, `/loop`, `/claude-api`, `/run`, `/verify`, `/run-skill-generator`, `/simplify`, `/security-review`, `/fewer-permission-prompts`, `/dataviz`). A separate **Workflow** category (`/deep-research`) "fans work out across many subagents and runs in the background." This three-tier taxonomy (hard-coded command / prompt-based skill / background workflow) is directly relevant to ebrain's own `ebrain <subcommand> --json` contract-first design (ADR-003 §3) — Claude Code arrived at almost the same layering. Source: [commands](https://code.claude.com/docs/en/commands) (full table, ~90 commands — includes the taxonomy legend).

**The full built-in command surface** (selected, grouped by relevance to an ebrain canon — not the complete ~90-row table, which lives at the cited URL):
- *Session lifecycle*: `/clear` (aliases `/reset`,`/new`), `/resume` (alias `/continue`), `/branch`, `/fork`, `/rename`, `/cd`, `/add-dir`, `/background` (alias `/bg`), `/exit` (alias `/quit`)
- *Context/cost*: `/compact`, `/context`, `/usage` (aliases `/cost`, `/stats`), `/rewind` (aliases `/checkpoint`, `/undo`)
- *Config/appearance*: `/config` (alias `/settings`, now accepts `key=value` directly, e.g. `/config theme=dark`), `/theme`, `/statusline`, `/tui [default|fullscreen]`, `/color` (prompt-bar accent color, syncs to Remote Control), `/focus` (quiet transcript view), `/scroll-speed`
- *Model/effort*: `/model`, `/effort`, `/fast` (fast mode toggle), `/advisor` (second-model consult)
- *Ship pipeline*: `/diff`, `/code-review`, `/simplify`, `/security-review`, `/review` (single-pass PR read), `/ultrareview`/`/code-review ultra` (cloud multi-agent)
- *Background orchestration*: `/tasks` (alias `/bashes`), `/batch` (worktree-per-unit fan-out), `/workflows`, `/goal`
- *Diagnostics*: `/doctor` (alias `/checkup`), `/debug`, `/heapdump`, `/feedback` (aliases `/bug`,`/share`)
- Misc UX sugar: `/powerup` (interactive feature tour with animated demos), `/insights`, `/team-onboarding`, `/radio` (a lo-fi radio stream — pure personality/branding touch)

Source: [commands](https://code.claude.com/docs/en/commands) full table.

**MCP prompts as commands**: any MCP server's exposed prompts auto-surface in the `/` menu as `/mcp__<server>__<prompt>` — directly relevant since ebrain already runs an MCP server; this is a ready-made pattern for exposing `ebrain` MCP tools as slash-invocable from inside a Claude Code session that's *orchestrating* an ebrain-launched agent. Source: [commands §MCP prompts](https://code.claude.com/docs/en/commands#mcp-prompts).

## (d) Theming

Built-in preset themes, selected via `/theme` or `/config` → Theme, stored as the `theme` setting: **`auto`** (matches terminal's detected light/dark background and follows OS appearance changes), **`dark`** (default), **`light`**, **`dark-daltonized`**, **`light-daltonized`** (colorblind-accessible), **`dark-ansi`**, **`light-ansi`** (use the *terminal's own* 16-color ANSI palette rather than Claude Code's truecolor palette — useful over restrictive terminals/SSH). Source: [settings §Available settings](https://code.claude.com/docs/en/settings) (`theme` row), [commands](https://code.claude.com/docs/en/commands) (`/theme` row).

**Custom themes** are plain JSON files at `~/.claude/themes/<slug>.json`, live-reloaded on file change (no restart), with three fields: `name`, `base` (one of the six built-in presets to start from), `overrides` (a map of semantic color-token names to values). Color values accept `#rrggbb`, `#rgb`, `rgb(r,g,b)`, `ansi256(n)`, or `ansi:<name>` (16 standard ANSI names). Selecting a custom theme stores `custom:<slug>` as the theme preference. `/theme` → "New custom theme…" opens an interactive per-token editor with live preview. This is a **semantic-token theming model**, the same philosophy ebrain's own `theme.ts` (SPRINT-TUI 6.2.2) is already committed to. The documented token set, grouped:

- **Text/accent**: `claude` (brand accent — spinner + assistant label), `text`, `inverseText`, `inactive`, `subtle`, `suggestion`, `permission` (dialog borders), `remember` (memory/CLAUDE.md indicators)
- **Status**: `success`, `error`, `warning` (also the auto-mode border color), `merged` (PR merged state)
- **Input box/mode indicators**: `promptBorder`, `planMode`, `autoAccept`, `bashBorder`, `ide`, `fastMode`
- **Diff rendering**: `diffAdded`, `diffRemoved`, `diffAddedDimmed`, `diffRemovedDimmed`, `diffAddedWord`, `diffRemovedWord`
- **Fullscreen-only** (background-fill tokens, N/A in classic renderer): `userMessageBackground`(+Hover), `messageActionsBackground`, `bashMessageBackgroundColor`, `memoryBackgroundColor`, `selectionBg`
- **Usage meter / speaker labels**: `rate_limit_fill`/`rate_limit_empty`, `briefLabelYou`/`briefLabelClaude`
- **Shimmer pairs** (animated-gradient light color for a spinner/border token): `claude`+`claudeShimmer`, `warning`+`warningShimmer`, `permission`+`permissionShimmer`, `promptBorder`+`promptBorderShimmer`, `inactive`+`inactiveShimmer`, `fastMode`+`fastModeShimmer`
- **Subagent colors**: 8 fixed named slots (`red_FOR_SUBAGENTS_ONLY` … `cyan_FOR_SUBAGENTS_ONLY`) so parallel subagents/tasks are visually distinguishable in the transcript — a subagent's `color:` frontmatter field picks one of the 8 names
- **Rainbow gradient** tokens for the `ultrathink`/`ultraplan` prompt keywords (`rainbow_<color>` × 7 + shimmer variants) — a pure personality/delight touch

Source: [terminal-config §Match the color theme / Create a custom theme / Color token reference](https://code.claude.com/docs/en/terminal-config#match-the-color-theme) (the single richest theming doc found).

Claude Code does **not** control the terminal's own background color scheme — themes only recolor what Claude Code itself draws; the terminal emulator's palette is out of scope, same constraint ebrain's TUI will have. Also relevant to ebrain's "cero hardcode de paleta" GATE 6.3.7 check: Claude Code's entire palette is late-bound through named tokens, never literal hex in call sites (inferred from the override-only customization model — **(observed/inferred)**, not a claim the docs make about their own source layout, but a reasonable inference from a token system this granular existing at all).

## (e) Sesiones

**Not tabbed** — confirmed both by omission (nothing in the docs describes a tab bar inside a single interactive session) and by contrast: the product's answer to "I want to watch several agents at once" is a **separate, dedicated full-screen dashboard**, `claude agents` ("agent view"), not tabs bolted onto the regular session UI. This is worth internalizing for ebrain: Claude Code's own architecture is "one session = one full-screen conversation" + "many sessions = a different screen entirely" — structurally close to what ADR-003 already proposes (tmux as the multi-session substrate, the TUI as a control-plane dashboard over it, `attach` as a full handoff rather than an embedded pane).

**Session storage/identity**: a session = a saved conversation tied to a project directory, stored locally as JSONL at `~/.claude/projects/<project>/<session-id>.jsonl` (30-day auto-cleanup, configurable), one line per message/tool-use/metadata entry (explicitly called an internal, version-unstable format — scripts should use `/export` or the hook `transcript_path` instead of parsing it directly). Sessions get an **auto-generated default display name** (`<dirname>-<2-char-suffix>`) if never explicitly named; `/rename`, `-n <name>` at launch, or accepting a plan (which names the session from the plan content) all set a real, resumable name. Source: [sessions](https://code.claude.com/docs/en/sessions).

**Resume/continue**: `claude --continue` (most recent session in cwd), `claude --resume` (opens the picker), `claude --resume <name>` (direct), `/resume` (in-session picker), `claude --from-pr <n>` (resume the session linked to a PR). The picker (`↑/↓` navigate, `Space` preview, `Ctrl+R` rename, `/`-or-any-char search, `Ctrl+A` widen to all projects on the machine, `Ctrl+W` widen to all worktrees, `Ctrl+B` filter to current branch) is itself a small, well-thought-out TUI component worth studying directly for ebrain's own `sessions list` panel (SPRINT-TUI 6.4.3) — row = name-or-summary + time-since-activity + message-count + branch; grouped by forked lineage (`/branch`/`/rewind`/`--fork-session` children nest under their root, expand with `→`). Source: [sessions §Use the session picker](https://code.claude.com/docs/en/sessions#use-the-session-picker).

**Branch vs. fork vs. rewind** (three distinct "make a copy" primitives, worth not conflating in ebrain's own vocabulary): `/branch` = switch yourself into a full copy of the conversation, original stays intact and resumable; `/fork` = spawn a *background subagent* that inherits full conversation and works a side directive while you keep going, result returns to your conversation when done; `/rewind`'s "Restore conversation" = revert *in place* to an earlier point in the *same* session (destructive to what came after, unless you'd branched first). Source: [sessions §Branch a session](https://code.claude.com/docs/en/sessions#branch-a-session), [commands](https://code.claude.com/docs/en/commands) (`/fork` row).

**Background tasks / background sessions — two different scopes worth separating**: (1) **background Bash** inside one session — `Ctrl+B` moves a running shell tool call to the background, output goes to a file, Claude can `Read` it later, tasks auto-terminate past 5GB output or (recent versions) under OS memory pressure after 30 min idle; visible via `/tasks`. (2) **Background sessions** — `/background` (alias `/bg`) detaches the *entire current conversation* to keep running unattended, freeing the terminal; these are full independent Claude Code processes managed by a **supervisor process** that survives terminal close and machine sleep, listed and dispatched from **agent view** (`claude agents`): a table grouped by state (Pinned / Ready for review / Needs input / Working / Completed), each row auto-summarized by a small Haiku-class model (throttled to ~1 rewrite/15s while working, up to every 4 min on long turns), with `Space` to peek-and-reply without leaving the table and `Enter`/`→` to fully attach (taking over the terminal) and `←` to detach back to the table. This "supervisor + peekable table + full-attach handoff" model is structurally almost identical to what ebrain's ADR-003 already proposes for tmux (`capture-pane` = peek, `attach`/`switch-client` = full handoff) — strong independent validation of that design, and a good source of extra row-affordances to borrow (state icon shape distinguishes *process alive* vs *exited-but-resumable* vs *sleeping-loop-with-countdown*; terminal tab title shows an awaiting-input count while the dashboard is open). Source: [agent-view](https://code.claude.com/docs/en/agent-view) (very detailed — read in full for the ebrain sessions panel design), [interactive-mode §Background Bash commands](https://code.claude.com/docs/en/interactive-mode#background-bash-commands).

## (f) Render stack (light touch, per rubric)

Publicly, Claude Code's CLI is a Node.js/TypeScript application. It is **widely reported in the public developer community** (blog posts dissecting error stack traces, GitHub issue threads referencing component names, general industry knowledge of what Anthropic's other public tooling uses) that the terminal UI is built on **Ink** (React reconciler targeting terminal output) — the same rendering approach as `gemini-cli` (confirmed in this same SPRINT's task 6.0.4 vendor clone, which has actual `.go`-free Ink/React source under `packages/cli/src/ui/`). This claim is **(observed/inferred)** — not independently re-verified against Claude Code's own source in this task (closed-source, and the task's hard constraint forbids reading any minified bundle even if reachable), but it is consistent with: (1) the "flicker" language used throughout the fullscreen-rendering docs, which reads exactly like the known Ink/React-reconciler-in-a-terminal failure mode (excessive full-tree re-renders causing visible redraw), and (2) Anthropic explicitly calling fullscreen mode a "research preview" that had to solve flicker and memory-growth problems from scratch — the kind of retrofit an Ink-based classic renderer would need. **No claim stronger than this should be treated as verified.** This is directly relevant to ebrain's ADR-003 rationale (Option A "Ink/React" rejected for RAM reasons) — Claude Code's own documented struggle with flicker/memory in long conversations is circumstantial support for that rejection, not proof of the specific framework.

## (g) Qué robar / qué evitar

**Steal:**

1. **Spinner verb + shimmer, but as a themeable/overridable primitive, not a hardcoded string.** Claude Code ships this as a first-class setting (`spinnerVerbs`, append/replace mode) — cheap, high personality payoff, zero RAM cost. Trivial to add to `tui/src/kit/` and directly asked-for in ADR-003's aesthetic brief.
2. **Semantic color tokens with shimmer pairs**, not literal hex anywhere in call sites. Claude Code's token table (§d) is a good starting shape for `tui/src/theme.ts` — steal the *category* breakdown (text/accent, status, input-mode-indicators, diff, subagent-colors) even if ebrain's exact token names differ.
3. **Permission-mode badge in the status bar** (`⏸ manual mode on`, `⏵⏵ accept edits on`) — cheap, always-visible state communication, directly reusable for ebrain's own future "launch flow" permission/frontier-lock UX (SPRINT-TUI 6.6.1).
4. **The plan-approval gate as a mode-selection menu** ("Approve and start in auto / Approve and accept edits / Approve and review manually / Keep planning / Refine further") — this is a strong pattern for ebrain's own advisor/launch flow (6.6.1): present the recommended lane, but make the actual "go" a small menu of concrete next-mode choices instead of a bare yes/no.
5. **Peekable background-session table + full-attach handoff** (agent view) is close to a direct blueprint for ebrain's Sessions panel — state-grouped rows, Haiku-cheap auto-summary throttled to avoid re-render/cost storms, `Space` = peek-without-leaving-the-table, `Enter` = full attach, `←` = detach. Steal the *throttle discipline* specifically (≤1 summary rewrite/15s while working, backing off to 4 min on long turns) as a template for ebrain's own tmux `capture-pane` poll-throttle requirement (ADR-003 §2, SPRINT-TUI 6.4.3).
6. **Rewind/checkpoint as "local undo" distinct from git** — a genuinely useful mental model (every prompt = a checkpoint; restore code/conversation/both independently) that's cheap to explain and valuable even for a control-plane TUI that isn't itself editing files.
7. **`/btw`-style no-tool side-question overlay** — worth considering for ebrain's Memory panel (6.5.2): a fast, cheap, doesn't-touch-context query path distinct from the full `ebrain q`/`think` round-trip.
8. **Classifier-gated "auto mode" instead of binary yes/no per action** — the multi-layer design (allow/deny rules first, then working-dir edits auto-approved, then everything else through a cheap classifier, with a hard fallback after repeated blocks) is a genuinely well-engineered permission model. Even a much simpler ebrain analog (e.g., "frontier-model launches always confirm explicitly, everything else follows the manifest's declared class") should borrow the *fallback-to-manual-after-N-blocks* circuit breaker.

**Avoid / skip:**

1. **Ink/React (or any reconciler-based render stack)** — already the explicit subject of ADR-003's rejection, and Claude Code's own documented flicker/memory problems in long sessions are circumstantial evidence *for* that call, not against it. Do not revisit this without new data.
2. **The sheer command surface (~90 built-ins + bundled skills + workflows + plugins).** This works for Claude Code because it's a general-purpose coding agent used by millions; ebrain's TUI is a small, single-operator daily cockpit. Resist copying breadth — SPRINT-TUI's own contract (`ebrain <subcommand> --json` first, panel second) already caps this correctly. Borrow the *taxonomy* (hard command / prompt-skill / background workflow), not the *count*.
3. **Full vim-mode emulation for prompt editing.** High implementation cost (motions, operators, text objects, visual mode) for a control-plane TUI whose primary text-entry surfaces are short (launch descriptions, prompt composer) rather than long-form editing. Not worth the tui-kit budget in F6.
4. **Fullscreen mode's mouse-capture/native-selection tradeoff complexity** (the whole `CLAUDE_CODE_DISABLE_MOUSE`/`_CLICKS` escape-hatch matrix). This exists because Claude Code has to reconcile "long scrollable conversation with copyable prose" against "flicker-free rendering" — a tension ebrain's TUI mostly avoids, since its panels are structured data (tables/gauges/lists) rather than long natural-language transcripts. Don't import this complexity preemptively; revisit only if a future panel needs freeform scrollback.
5. **The classifier-based auto mode's actual implementation** (a live model call per gated action) — correct for a product with Anthropic's inference budget and trust surface, wrong for a 4GB-RAM Celeron cockpit with a $10/mo capped routing budget. If ebrain wants an "auto" permission tier at some point, it should be static rule-based (manifest classes + explicit confirm-on-frontier), not a live classifier call.
6. **Session-picker breadth** (cross-project, cross-worktree, cross-machine search) is over-scoped for ebrain's tmux-session list, which is inherently local-machine and short-lived by design (ADR-003: sessions are ephemeral `ebr-<agent>-<slug>` tmux panes, not a permanent JSONL-backed conversation archive). Don't try to replicate Claude Code's session-archaeology UX on top of tmux — that's the eBrain memory system's job, not the TUI's.

## Top UX patterns to steal for ebrain

1. Themeable spinner verbs + shimmer gradient (cheap, high personality, directly settings-driven in Claude Code).
2. Semantic color-token theme file (not hex-in-callsites), with a shimmer-pair convention for animated accents.
3. Always-visible mode badge in the status bar (manual / accept-edits / plan / bypass, ebrain analog: local/read-only vs launch-armed vs frontier-confirmed).
4. Plan-approval-as-menu (concrete next-mode choices, not yes/no) — steal for the advisor/launch flow.
5. Peekable, state-grouped, auto-summarized background-session table with throttled updates and full-attach handoff (agent view) — near-direct blueprint for the Sessions panel.
6. Local "rewind" mental model (checkpoint per prompt, restore code/conversation/both independently) distinct from git.
7. No-tool side-question overlay pattern (`/btw`) for a cheap, non-destructive query path.
8. Circuit-breaker fallback to manual approval after repeated auto-mode blocks — borrow the *fallback discipline*, not the live-classifier mechanism.
